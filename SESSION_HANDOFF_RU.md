## 2. Как работать с Андреем

- Общайся по-русски. В начале работы коротко подтверди, что именно будет сделано, затем приступай к проверкам и работе; не начинай с молчаливых вызовов инструментов.
- Андрей предпочитает прямую работу по запросу, короткие промежуточные сообщения и проверки только необходимого объёма: не трать время и токены на повторные или несвязанные проверки.
- Соблюдай формулировку объёма задачи. Если сказано «только это исправь, остальное не трогай», меняй только необходимый участок; не используй задачу как повод для рефакторинга, переименований, чистки или дополнительных улучшений.
- Если важное требование действительно неоднозначно, задай один или несколько конкретных наводящих вопросов до изменения кода. Сначала выясни факты из проекта сам; не спрашивай пользователя о том, что можно проверить чтением кода или Git. Сформулируй краткий пересказ ожидаемого поведения и дождись подтверждения, если выбор меняет механику.
- При неоднозначной или крупной задаче проектные инструкции требуют использовать навыки `grill-me` и `grilling`; если они отсутствуют в новой среде, установи их командой `npx skills@latest add mattpocock/skills --skill=grill-me --skill=grilling` и следуй им. Не превращай ясный небольшой запрос в длинное интервью.
- Не заявляй, что проверял игру на телефоне, если проверка была только в настольном Chromium или эмуляции.

## 3. Обязательный Git preflight и сохранность изменений

Перед любой правкой заново проверь актуальность репозитория — даже если прошлый чат сообщает, что рабочее дерево было чистым:

```bash
git fetch origin main
git status --short --branch
git remote -v
git rev-parse HEAD
git rev-parse origin/main
git log -5 --oneline origin/main
```

Если есть пользовательские незакоммиченные изменения, сохраняй их и не включай в свою задачу без разрешения. Не выполняй `git reset`, принудительный push, `git clean` и другие разрушительные операции. Если `main` разошёлся с `origin/main`, выясни состояние и безопасно согласуй дальнейший порядок; не перезаписывай удалённую ветку.

Каждое самостоятельное изменение фиксируй отдельным коммитом с ясным сообщением на русском. После проверок отправляй обычным `git push origin main`. Затем проверь, что `origin/main` содержит именно отправленный SHA и что локальное дерево не содержит неожиданных изменений. Если коммит, push или публикация не удались, приведи точную ошибку и конкретно укажи, что нужно для продолжения.

## 4. Структура и способ запуска

Это статический проект без обязательного сборщика и package manager. Не переводить существующий код на ES-модули и не менять порядок обычных `defer`-скриптов без необходимости: модули используют существующие глобальные функции и inline-обработчики.

Основные файлы:

- `index.html` — экраны, HUD, сенсорное управление, подключение библиотек и JS.
- `style.css` — оформление и мобильный интерфейс.
- `js/00-state.js` — состояние игры, настройки, константы и сохранения.
- `js/01-feedback.js` — HUD, сообщения, звук и визуальная обратная связь.
- `js/02-rendering.js` — Three.js-сцена, renderer и охотник.
- `js/03-models.js` — загрузка и анимация моделей.
- `js/hunter-rig.js` — покадровая сборка/анимация частей модели охотника; подключён перед `03-models.js`.
- `js/04-world.js` — поверхности, геометрия мира, лестницы и часть коллизий.
- `js/05-entities.js` — создание локаций, лестниц, врагов и объектов.
- `js/06-ui.js` — меню и игровые действия.
- `js/07-gameplay.js` — игровой цикл и движение.
- `TODO.md` — список этапов/задач с отметками выполненного; перед обсуждением оставшегося сверяйся с файлом и кодом, не выдавай старые планы за гарантированно актуальный приоритет.

Локальный сервер из корня репозитория:

```bash
python3 -m http.server 8000
```

Открыть `http://127.0.0.1:8000/`. Для проверки WebGL в headless Chromium используй Chromium с флагами `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader` (и необходимыми для sandbox `--no-sandbox`/`--disable-dev-shm-usage`). Обычный Chromium без SwiftShader в этой среде может не создать WebGL-контекст; это ограничение запуска, а не само по себе ошибка игрового кода.

## 5. Инварианты, которые нельзя нарушать побочными изменениями

- Игра рассчитана на горизонтальную ориентацию. Сохраняй экран «Поверните устройство», fullscreen и блокировку landscape.
- Не меняй Three.js r128, CDN-пути GLTFLoader/MeshoptDecoder и их предусмотренные резервные адреса.
- Не ломай сенсорное управление, интерфейс или совместимость с мобильными браузерами.
- Сохраняй направление охотника, управляемое через `modelFlip`, клавишу `T` или `?flip=1`.
- Не пережимай, не конвертируй и не переименовывай аудио-, графические и 3D-ассеты; не перемещай их без необходимости и явного основания. В частности, сохраняй `source/hunter.glb`, `hunter_light.glb` и существующую rig-анимацию.
- В `getFloorHeightAt` сохраняй выбор самой высокой достижимой поверхности и штатные пороги: подъём до `+0,6`, спуск до `−1,35`. Особые сценарии падения должны обрабатываться адресно, не ослаблением этих порогов для всех перемещений. У ступеней должны сохраняться рабочие опорные поверхности/коллизии.
- Не возвращай отдельную кнопку переката: в текущем управлении перекат выполняется двойным тапом. Захват цели — отдельная контекстная кнопка в радиусе; захват автоматически снимается за пределами радиуса.
- Учитывай уже внесённые улучшения загрузки/производительности и текущие формы локаций; не переписывай механики без прямого запроса.

## 6. Состояние лестниц на момент передачи

В последних коммитах исправлен спуск по лестницам (`43d9713`, затем `4c2840f`). Последний опубликованный фикс затрагивал только `js/04-world.js` и `js/07-gameplay.js`:

- при боковом или заднем попадании сверху в лестничный проём охотник должен перейти на наклонную лестничную поверхность, а не остаться висящим на высоте верхнего этажа;
- проход под серединой лестницы на нижнем этаже не должен переключать персонажа на ступени;
- падение с верхнего этажа на нижнюю площадку мимо ступеней снимает 10 HP один раз; приземление на ступени не должно вызывать этот урон;
- обычные пороги шага `+0,6/−1,35` сохранены.

Перед повторным изменением этой механики сначала прочитай актуальные `getFloorHeightAt` и `updateHunterFloor` в `js/04-world.js`, их вызовы в `js/07-gameplay.js` и построение лестниц/проёмов в `js/05-entities.js`. Не возвращай предыдущую ошибку прохода снизу и не расширяй изменение на другие механики. Локальная и опубликованная версии на момент этого handoff прошли Playwright-проверку с каменной, деревянной и верёвочной лестницами; в проверенных сценариях не было новых ошибок консоли или HTTP 4xx/5xx. Это настольный браузерный тест, не тест на телефоне.

## 7. Минимально достаточная проверка перед публикацией

Выбирай проверки по затронутому сценарию. Для изменения JavaScript обязательны:

```bash
node --check <каждый-изменённый-js-файл>
git diff --check
```

Кроме этого:

1. Запусти затронутый игровой сценарий локально через HTTP-сервер в Chromium/Playwright; для WebGL используй SwiftShader-флаги выше.
2. Проверь консоль JavaScript и ответы сети на новые 404/ошибки. Не проверяй несвязанные механики «на всякий случай».
3. Сделай один коммит на отдельное изменение и обычный push в `origin/main`.
4. Дождись обновления GitHub Pages. Проверь HTTP-ответ сайта и именно опубликованный сценарий/затронутые файлы, а не только локальную копию.
5. В итоговом сообщении кратко укажи, что изменено, SHA коммита, что проверено локально и на Pages, результат консоли/ошибок HTTP и ограничения проверки. Если Page ещё не развернулся или проверка не удалась — сообщи это явно.
